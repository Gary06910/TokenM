# Token M MVP implementation plan

Status: **frozen for the first implementation pass** (2026-08-17)

This document records the architecture contract for the private-beta MVP. The local checkout is the source of truth. Existing Token Monitor compatibility surfaces remain supported unless this document explicitly introduces a new `/v1` surface.

## 1. Current architecture

- `src/electron/main.js` owns the Electron process, settings/credential persistence, IPC, local collection, hub modes, and renderer windows. Renderer isolation is already enabled (`contextIsolation: true`, `nodeIntegration: false`).
- `src/agent/agent.js` runs the same device collection runtime without UI and posts the privacy-filtered sync payload.
- `src/hub/server.js` is the self-hosted Node hub. It persists device records to JSON and exposes authenticated `/api/ingest`, `/api/stats`, `/api/stats/stream`, subscriptions, history, and device deletion.
- `worker/src/index.js` is the Cloudflare equivalent. It currently routes every request to one SQLite Durable Object named `hub` and protects private `/api/*` routes with one `TOKEN_MONITOR_SECRET`.
- `src/shared/` is the only source of truth for portable shared logic. `worker/src/shared/` is generated by `npm run sync:worker` and must not be edited directly.
- The Electron widget supports `local`, `client`, and `host` hub modes. Client mode consumes the SSE stats stream and uploads local usage; host mode embeds the Node hub and writes its own records in-process.
- Credentials belong to the main process and `credentials.json`; the renderer receives a default-deny redacted settings view. Existing hub secrets are legacy exceptions.
- Hub source identity is tracked independently of the desktop version. After final Hub/Worker changes stabilize, run `npm run update:hub-build` once, which also synchronizes generated Worker shared copies.

## 2. Proposed architecture

```text
Codex Stop hook                 Codex App Server (when controlled)
      |                                     |
      +---------- normalized completion ----+
                            |
                    127.0.0.1 hook bridge
                            |
                   persistent desktop outbox
                            |
             POST /v1/events (device credential)
                            |
                 Cloudflare Worker router
                            |
            TenantDO: idFromName("tenant:<id>")
                            |
        per-installation Web Push with event dedupe
                            |
               Android / iPhone Home Screen PWA
```

One deployed Worker serves three roles:

1. Existing self-hosted-compatible `/api/*` traffic goes to the unchanged legacy `HubDO` named `hub`.
2. Managed `/v1/*` traffic is routed by the tenant id embedded in a scoped credential to a distinct `TenantDO`.
3. `worker/public/` is served as Worker Static Assets for the PWA at the same `workers.dev` HTTPS origin.

No managed endpoint can read or list another tenant. There is no global tenant stats endpoint in the MVP.

## 3. Codex completion detection

The primary detector is the official Codex `Stop` lifecycle hook. Current official documentation defines common stdin fields (`session_id`, `cwd`, `hook_event_name`) plus Stop-specific `turn_id`, `stop_hook_active`, and `last_assistant_message`. Token M reads only identifiers and `cwd`; it does not persist or upload `transcript_path` or `last_assistant_message`.

The user must explicitly enable integration. The installer/desktop logic:

1. reads `~/.codex/hooks.json` without following a symlink;
2. creates a timestamped backup before the first change;
3. merges one recognizable Token M command into `hooks.Stop` without replacing other hooks;
4. uses a short timeout and a non-blocking local handoff;
5. tells the user to review/trust it with Codex `/hooks` when required;
6. disables by removing only Token M's exact entry and preserving every other entry.

The hook posts JSON to a loopback-only endpoint owned by the Electron main process. A per-installation local bridge token prevents browser-origin requests from fabricating events. The bridge returns the JSON shape expected by a Stop hook and never delays a turn on cloud delivery.

When Token M itself controls a Codex App Server, an adapter may feed its documented `turn/completed` notification into the same normalizer. `completed` becomes `codex.turn.completed`; `interrupted` and `failed` are reserved for later event types and are not pushed as successful completions in this MVP.

No transcript watcher is enabled. A future fallback must parse a stable semantic completion record, be labeled as a fallback, and ship focused tests; file modification alone is never completion.

Normalized MVP event:

```json
{
  "eventId": "evt_<deterministic sha256 tuple>",
  "type": "codex.turn.completed",
  "deviceId": "dev_<random id>",
  "sessionId": "<Codex session_id>",
  "turnId": "<Codex turn_id>",
  "status": "completed",
  "project": "<basename of cwd, max 80 chars>",
  "summary": "Codex task completed",
  "occurredAt": "<ISO-8601 UTC>",
  "durationMs": 512000
}
```

`durationMs` is optional. `eventId` is deterministic over version, device id, session id, turn id, type, and status so repeated hook delivery survives process restarts without creating a new logical event.

## 4. Multi-tenant model

- `tenant/user`: one private-beta user boundary, identified by a cryptographically random 128-bit `tenantId`.
- `desktop device`: random `deviceId`, display hostname, credential hash, created/last-seen/revoked timestamps.
- `mobile installation`: random `installationId`, display name, independent credential hash, push subscription, timestamps, and revocation state.
- `push subscription`: endpoint plus `p256dh` and `auth` keys, stored only inside its tenant DO.
- `pairing challenge`: random challenge id, HMAC of a 256-bit secret, issuing device, expiry, and used timestamp.
- `notification event`: privacy-minimal event plus per-installation delivery state for idempotent retries.

Managed bearer formats are opaque capabilities with a version prefix:

```text
tm_d1.<tenantId>.<deviceId>.<256-bit secret>
tm_m1.<tenantId>.<installationId>.<256-bit secret>
tm_p1.<tenantId>.<challengeId>.<256-bit secret>
```

The Worker parses only enough to select the tenant DO. The DO validates the complete presented capability with constant-time comparison against `HMAC-SHA-256(TOKEN_M_CREDENTIAL_PEPPER, capability)`. Raw capabilities are never stored server-side or logged.

Tenant creation is gated by `TOKEN_M_ENROLLMENT_SECRET`, a private-beta enrollment capability. It can create a new isolated tenant but cannot read or write any tenant data. It is entered once in the Desktop UI or supplied by an operator; it is not embedded in builds or the PWA.

## 5. Pairing protocol

1. An enrolled desktop calls `POST /v1/pairings` with its device bearer.
2. The TenantDO creates a 256-bit random secret, stores only its HMAC, and sets a 10-minute expiry.
3. Desktop renders `https://<worker>/pair#token=tm_p1...` as a QR code. Fragment use keeps the token out of HTTP request targets, proxy logs, and referrers.
4. The PWA reads and immediately removes the fragment from visible history, then calls `POST /v1/pairings/redeem` with the token in the JSON body.
5. The DO atomically verifies unused + unexpired, marks it used before issuing credentials, creates a mobile installation, and returns a one-time mobile bearer.
6. Replay, expiry, random token, malformed token, and wrong-tenant routing return a generic rejection without revealing which component matched.
7. PWA stores the mobile bearer in IndexedDB, not cookies or URLs. It then asks for notification permission only after a user gesture and registers its PushSubscription.

The QR contains no desktop credential, mobile credential, VAPID private key, or reusable tenant secret.

## 6. Authentication model

- Legacy `/api/*`: unchanged `TOKEN_MONITOR_SECRET` behavior for self-hosted Token Monitor compatibility.
- Managed desktop endpoints: `Authorization: Bearer tm_d1...`.
- Managed mobile endpoints: `Authorization: Bearer tm_m1...`.
- Pair redemption: pairing capability in request JSON; it is one-time and short-lived.
- Enrollment: `x-token-m-enrollment-secret`, compared with `TOKEN_M_ENROLLMENT_SECRET`; this capability creates tenants only.
- Credential hashing pepper: `TOKEN_M_CREDENTIAL_PEPPER`, Worker secret only.
- Web Push signing: `TOKEN_M_VAPID_PRIVATE_KEY` and `TOKEN_M_VAPID_SUBJECT`, Worker secrets only. `TOKEN_M_VAPID_PUBLIC_KEY` is the only VAPID material returned to the PWA.

Desktop and mobile credentials are separate and independently revocable. Device identity in an event is derived from the authenticated credential; a mismatched payload `deviceId` is rejected.

## 7. Web Push flow

The Worker uses a Worker-compatible WebCrypto Web Push implementation (planned dependency: `@block65/webcrypto-web-push`, justified in this plan rather than a Node-only `web-push` package). VAPID private material never enters source, static assets, QR data, renderer IPC, or logs.

For each accepted event, TenantDO creates a delivery state per active mobile installation and sends a minimal encrypted payload:

```json
{
  "eventId": "evt_...",
  "title": "Token M",
  "body": "Codex task completed\nProject: token-m",
  "url": "/?event=evt_...",
  "tag": "evt_..."
}
```

- `201/202`: mark that installation delivered.
- `404/410`: delete the expired subscription and mark terminal.
- `429/5xx/network`: retain pending delivery and return retryable `503` to Desktop.
- Retries send only pending installations. A Web Push `Topic`/notification `tag` derived from `eventId` reduces provider/client duplicates.
- Multiple installations are independent. One expired endpoint does not prevent other phones from receiving the event.

## 8. PWA architecture

`worker/public/` contains framework-free static assets to keep the bundle small and auditable:

- `index.html`: pair/onboarding/status UI.
- `app.js`: pairing redemption, IndexedDB credential storage, service-worker registration, permission flow, subscription registration, status, test push, and unpair.
- `service-worker.js`: `push`, `notificationclick`, activation/update handling.
- `manifest.webmanifest`: `name`/`short_name` Token M, stable `id`, `start_url`, `display: standalone`, icons, colors.
- icon assets and focused unit/source-contract tests.

Android gets normal install and notification guidance. On iOS/iPadOS, Token M detects whether it runs in standalone display mode. If not, the notification action is disabled and the UI explicitly instructs the user to add Token M to the Home Screen and reopen it there. This follows Apple's Home Screen Web Push model (iOS/iPadOS 16.4+). Unsupported browsers, denied permission, missing PushManager, expired subscription, and offline state all render explicit status.

## 9. Desktop integration

New main-process modules own managed-cloud credentials, local hook input, normalization, outbox persistence, and network retry. Renderer code sees only:

- cloud URL;
- enrolled/bound counts and display names;
- hook enabled/trust guidance state;
- pairing URL/expiry needed to render a QR;
- last delivery/error status.

The renderer never receives the desktop bearer, enrollment secret after use, local hook bridge token, or raw pairing-token storage state beyond the short-lived pairing URL requested by the user.

Electron IPC contract is defined in `docs/token-m-api.md`. Existing local/client/host usage collection is not replaced. Managed completion notifications are an orthogonal runtime and can coexist with all three hub modes.

## 10. API endpoints

The frozen request/response contract is in `docs/token-m-api.md`. Summary:

```text
POST   /v1/desktop/enroll
GET    /v1/desktop/status
POST   /v1/pairings
POST   /v1/pairings/redeem
POST   /v1/events
GET    /v1/mobile/status
PUT    /v1/mobile/subscription
POST   /v1/mobile/test
DELETE /v1/mobile
```

All `/v1` JSON responses are `Cache-Control: no-store`. CORS is restricted to the Worker's own PWA origin for mobile endpoints; desktop endpoints accept non-browser HTTPS clients. Methods and content types are strictly validated.

## 11. Durable Object data model

Each `TenantDO` uses its own SQLite-backed Durable Object storage namespace:

```text
meta                         -> schemaVersion, tenantId, createdAt
device:<deviceId>            -> name, credentialMac, createdAt, lastSeenAt, revokedAt
mobile:<installationId>      -> name, credentialMac, subscription, permission, timestamps
pair:<challengeId>           -> tokenMac, deviceId, expiresAt, usedAt
event:<eventId>              -> normalized event, expiresAt, per-installation delivery states
rate:<scope>:<window>        -> bounded request counter
```

Pairings are retained only long enough to enforce replay rejection and are cleaned opportunistically. Event dedupe records default to seven days and are also cleaned in bounded batches. The schema is versioned. No key is shared between tenant objects.

## 12. Security and threat model

Primary threats and controls:

- Cross-tenant access: unguessable tenant ids plus per-record capability validation inside the selected DO; no global list/read route.
- Stolen shared legacy secret: it grants only the legacy `HubDO`, never `/v1` tenants.
- Pair token disclosure: fragment transport, 256-bit entropy, 10-minute TTL, atomic one-time use, generic failures.
- Credential leakage: store raw credentials only in Electron credential storage or PWA IndexedDB; redact IPC/logs/errors; VAPID private key is a Worker secret.
- Renderer compromise: context isolation remains enabled; privileged actions are narrow IPC calls; raw managed credential never crosses preload.
- Event spoofing/replay: authenticated device binding, strict schema, deterministic `eventId`, DO dedupe, bounded clock skew validation.
- Push endpoint lifecycle: validate endpoint HTTPS and key sizes; delete on 404/410; never log subscription keys.
- Resource abuse: required private-beta enrollment capability, per-tenant request/body limits, bounded records and cleanup.
- Privacy: never read or upload prompt, full assistant response, transcript, source, absolute paths, provider credentials, or Codex credentials. `project` is only a sanitized directory basename.

## 13. Retry and dedupe

Desktop outbox is an atomic JSON document under Electron `userData` with schema version, pending events, attempt count, next-attempt timestamp, and last machine error code. Enqueue is durable before network send. Delivery is serialized and uses exponential backoff with jitter (1 second base, 15 minute cap). Restart reloads pending items.

Only a successful 2xx removes an event. `401/403` suspend delivery and surface credential repair; `400/413` retain the item as terminal-visible rather than looping; network/429/5xx retry. Server duplicate acceptance is 200 with `duplicate: true`.

TenantDO writes an event/delivery record before sending. A retry with the same `eventId` sends only installations still pending. Completed or terminal installations are not sent again.

## 14. Migration and backwards compatibility

- `/api/*`, Node hub behavior, local/client/host modes, `TOKEN_MONITOR_*` variables, device sync wire shapes, and generated shared-code rules remain intact.
- User-visible branding changes to Token M. Keep npm package name, `appId`, updater repository, protocol identifiers, and `TOKEN_MONITOR_*` compatibility names for the MVP.
- Preserve the existing user-data location to avoid silently losing settings/credentials when `productName` changes. A later explicit migration can rename it with verified copy/rollback.
- Worker deployment name may become `token-m`; the Durable Object binding `HUB` and `HubDO` migration remain. Add `TENANTS`/`TenantDO` as a new SQLite migration rather than replacing the legacy namespace.
- MIT license and original attribution remain unchanged.

## 15. Test strategy

- Unit tests: token parsing/MAC validation, event normalization/privacy, deterministic IDs, outbox persistence/backoff, hook merge/restore, PWA state decisions, push response classification.
- Worker tests: tenant routing/isolation, enrollment, desktop/mobile auth, pair TTL and replay, event dedupe, multi-phone delivery, 404/410 cleanup, transient retry, legacy `/api/*` regression.
- Electron source/IPC tests: credentials stay main-process-only, settings redaction, pairing/status calls, UI wiring, Token M branding.
- Contract tests use the same fixtures across Desktop and Worker DTOs.
- Final commands: `npm run lint`, `npm test`, `npm run verify`; then Worker dependency install and `npx wrangler dev` or the repository's supported dry-run/smoke path.
- Android and iPhone outcomes remain `real-device verification pending` until physical tests are performed.

## 16. Free-tier deployment strategy

As of this plan date, Cloudflare documents SQLite Durable Objects on Workers Free, a 100,000 request/day Workers and DO allowance, and 5 GB total DO storage. Worker Static Asset requests are free/unlimited and assets have no additional storage charge. This is ample for at most ten private-beta users with event-driven traffic. If a free limit is exceeded, operations fail rather than silently billing on the Free plan; monitoring should surface this.

Use one `workers.dev` HTTPS deployment, Worker Static Assets, two SQLite DO classes, and standards-based Web Push. No domain purchase, Apple Developer membership, Google Play account, Firebase paid plan, SMS, database, or push SaaS is required.

Production deployment still requires a human to log in to Cloudflare, generate VAPID/enrollment/pepper secrets, configure them with Wrangler, and run deploy.
